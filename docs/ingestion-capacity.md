# 入库容量验证

容量结论必须记录实际发送量、接收确认、落库序号、队列恢复和对正常业务的影响。
自然流量下队列归零不证明峰值容量；gRPC 的 ACK 只证明接入层接受，必须再核对 PostgreSQL。

## 有界合成流量工具

`server/cmd/ingestload` 使用专用测试机现有的 mTLS 身份上报事件，不注册新主机，不启动进程、执行命令或发起模拟目标连接。
合成记录始终带 `acceptance_test=true`、唯一的 `acceptance_run` 和从 0 开始的 `acceptance_sequence`。
每 100 条包含 95 条进程、3 条网络、2 条 DNS，带进程/父进程 GUID 以覆盖相应索引写入；网络与 DNS 引用同组进程。
网络目的为 TEST-NET，DNS 使用 `.example` 保留域。
样本采用 Linux 进程形态，不用于推断 Windows 采集与检测容量。
这验证的是良性混合事件通路，不代表高告警率、关联、AI 研判或处置能力的容量。

在 `server/` 构建：

```bash
CGO_ENABLED=0 go build -o /tmp/openxdr-ingestload ./cmd/ingestload
```

将工具放到已授权的专用测试机，由其现有安全配置提供 `OPENXDR_SERVER`、`OPENXDR_CA`、
`OPENXDR_CERT`、`OPENXDR_KEY`。不要复制证书私钥到压测控制机，也不要将配置值打印到日志。

```bash
/tmp/openxdr-ingestload -agent-id "$TEST_AGENT_ID" -source-ip "$TEST_IP" \
  -run-id "$UNIQUE_RUN_UUID" -rate 10 -duration 10s
```

- `rate` 必须为 1–1000，`duration` 必须为 1–60 秒整数；每轮最多 60000 条。
- 按 ticker 限速，发送变慢时不通过突发补发追赶计划；总截止时间为计划时长加 10 秒。
- 接收 SIGINT/SIGTERM 时取消请求并尽量输出部分发送报告。错误、超时、确认不一致均非零退出，**不重连、不自动重投**。
- `sent` 是客户端已提交给 gRPC 流的数量，`acknowledged=null` 表示未拿到确认，不代表服务端未收到。
  超时或停止后先按 run ID 查询副作用，不能直接重跑同一轮。
- `complete=true` 只表示所有计划事件发送且接收数量一致；实际速率须由 `firstEvent`、`lastEvent` 与发送数计算，
  不能把参数中的计划速率当作实测速率。

## 生产执行与验收

1. 先确认正常流量无持续积压，主从同步、采集端健康。用 100 条验证身份、完整落库、95/3/2 分布和无意外告警。
2. 每轮使用新的 run ID，逐级增加速率；逐轮验收和恢复后才开始下一轮，不能把未消化的上一轮当新基线。
3. 约每 5 秒采样发布/处理计数、处理失败、NATS 待办、同步备库和高频正常资产的最新事件年龄。
   本次保护阈值：启动时正常资产年龄不超过 5 秒；运行中连续两次超过 10 秒或复制延迟超过 2 秒、
   待办超过 250 条消息、出现处理失败或同步备库退出时停止。消息可能包含多条事件，不能把消息数当事件数。
4. 按测试资产 ID、发送时间范围和 `acceptance_run` 查询事件；核对总量、唯一序号数、最小/最大序号、分类及关联告警。
   索引先限定资产和时间，禁止为一次压测在整个 events 表上无界扫描 JSON。
5. 完成后等待队列与正常资产事件年龄恢复；记录恢复耗时、全部失败轮次与停止原因，不能只保留最佳结果。
   保留明确标记的合成事件用于对账，随正常保留期清理，不把它们计为真实攻击。

正常资产“事件年龄”是时效性观察，不是每条事件从接收到提交的延迟分布；没有逐事件提交时刻时不报告 P95。
单个测试资产主要考验一个资产分片；多资产、多分片、真实检测命中和故障期间容量须分别验证。
