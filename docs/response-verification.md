# 响应效果复核（开发中）

Agent 的 `succeeded` 是动作回执，不等于预期安全效果成立；`unknown` 也不等于动作没有执行。
人工复核、系统核验与会话 AI 核验按来源分开存储，不覆盖指令状态、退出码或完成时间，不自动重试处置。

## 接口

`POST /api/commands/{id}/verifications` 接受：

```json
{
  "outcome": "inconclusive",
  "expected": "隔离后禁止目标业务连接，同时保留管理通道",
  "observed": "目前只有单侧连接记录，无法验证策略完整生效",
  "eventIds": []
}
```

- `outcome` 为 `effective`、`ineffective` 或 `inconclusive`。这是复核人的判断，不是机器验证标签。
- `expected` 与 `observed` 必填，各最多 4000 字节。明确结论需 1–20 个不同的非零事件 ID；不确定结论允许没有事件。
- 证据必须属于指令目标资产，事件时间不得早于指令创建时间或晚于复核时间；这只验证来源与时序，不证明事件足以支持结论。
- 身份从登录上下文和数据库用户取得，不能提交 reviewer/角色/归组字段。沿用 HTTP 写权限门槛，事务内再检查当前资产组的 analyst/admin 权限；未分组资产只有全局 admin 可写。
- 请求体上限 16 KiB，未知字段和尾随 JSON 拒绝。证据快照总量最多 1 MiB。

`GET /api/commands/{id}/verifications` 返回 `{items, truncated}`，最近 100 条，倒序稳定排序。
列表包含复核内容及证据 ID、时间、来源、类别，不展开证据原文，避免批量返回大量日志。
无权限与没有记录都返回空列表；读取同时要求复核时历史组和资产当前组的 viewer 权限，全局管理员不受限。

`GET /api/commands/{id}/verifications/{verificationId}` 返回一条复核的完整留存快照，包括事件原文。
必须同时匹配指令 ID 和复核 ID；复用列表的历史组/当前组权限条件，组外与不存在都返回 404。
该接口读保存的快照，不重新读取可能已清理的 events；单条证据体在写入时限制为 1 MiB。

## 机器与会话核验

人工 POST 接口保持用户身份与组权限检查，固定写 `source=human`、`method=manual_review`；模型不能借该接口冒充人。
Pi 的 `verify_command` 工具仅允许当前运行会话所属组的指令，由服务端派生 `ai:session:<id>`，不能提交来源或复核人。
返回与历史读取增加 `source`（human/system/ai）、`method`、可选 `sessionId`、`context`；界面分别标明来源与下发前/后证据。

- 所有非 succeeded 状态（包括 unknown）的机器结论只能是 inconclusive。没有后验正证据时，succeeded 也只能记 inconclusive。
- 当前确定性核验仅支持 kill_process：同资产、下发后、source=agent、class_uid=1007、规范化 process_guid 与进程 PID 精确匹配的退出事件才支持 effective；完成后匹配的进程存续事件可供 AI 核验 ineffective。PID/GUID/IP 字面提及、父进程、普通文件或其他目标的事件都不是证明。
- 下发前的退出事件只保存在 `context`，不能冒充下发后效果证据；其他动作尚无确定性状态探针时保留 inconclusive。
- 启用 containment 时，其 Tick 末尾自动核验最近 24 小时已归组、非 exec、终态或 unknown 的指令；每轮最多 500 条未核验或等待退出证据升级的记录。后续到达的匹配退出事件可补记 effective，不重发原动作。
- 系统核验固定 `system:containment`，按指令/回执状态/结论派生幂等身份；重复或跨节点并发巡检不重复追加相同系统记录。AI 与人工意见保持来源独立。

## 存储与审计

`command_verifications` 是追加记录：保存复核人、时间、复核时归组、当时指令状态、意见和原始事件快照。
资产、指令、用户与成员资格在写事务内锁定，证据读取与审计写入也在同一事务；任一步失败全部回滚。
`command_verification_recorded` 审计关联指令 ID、复核 ID、结论与证据 ID，不把原始日志复制进审计详情。

原始事件清理不删除已保存的证据快照；删除指令会级联删除它的复核记录。当前没有复核自动保留期策略，
也没有修改/删除复核的 API。复核时归组不是指令下发时归组，不能据此声称已追溯旧版指令的历史授权。

## 资产详情入口

「资产详情 → 指令 → 效果复核」打开抽屉：按当前角色显示复核表单或只读历史。
表单默认不确定结论，校验说明字节长度、证据 UUID、去重及数量；明确结论必须引用事件。
保存时禁用表单并显示进度，失败保留输入且提示先刷新检查是否已保存。
历史按页展示，证据原文仅展开时请求；失败与空记录分别显示，中文和英文同步。
复核查询按用户/角色/组成员信息隔离缓存，抽屉关闭后移除缓存；资产换组重建抽屉。

前端通过类型检查、构建和 lint；这不替代浏览器视觉与生产权限场景验收。

## Pi 回执复查入口

新增只读 `command_status` 工具，参数 `{"command":"指令 UUID"}`；不依赖该组是否配置 SQL 查询身份。
只查当前会话组内资产的已有指令，资产换组后旧会话不能继续查询；不存在或组外使用相同错误。
返回指令/资产 ID、类型、状态、创建/完成时间、退出码及截断后的标准输出/错误，不重新执行、不修改状态。
`effect=not_assessed_by_this_tool` 与 `retry=not_authorized_by_this_tool` 明确此工具未评估效果或批准重试。
它不读取人工效果复核，不替代后置条件检查；succeeded 仅是回执，pending/sent/unknown 不能证明未执行。
真实 PostgreSQL 测试覆盖六种状态、输出限制、换组、参数拒绝及查询不新增指令；未做真实 Pi/Agent 端到端验收。

### 执行回执中的效果边界

`exec` 正常返回仍保留原指令字段，同时附加 effect=not_assessed_by_this_tool 与 retry=not_authorized_by_this_tool。
成功、失败或不支持的动作回执都不等于效果复核，也不授权再次执行。
未知回执、等待取消/超时、数据库读取回执失败均保留指令 ID，指向 command_status，并禁止自动重试；
数据库错误不泄露原始连接错误。停止会话补齐的工具结果明确表示未取得完整结果，不声称动作未执行。
这些是工具数据与提示的语义边界，不是模型遵守指令的实测保证，也未新增自动重试策略。

### 回执存储错误传播

服务端 Complete 现在返回持久化结果；数据库写入失败、非法指令 ID 或不属于当前 Agent 的回执返回错误，
gRPC 指令流结束并解除在线通道，不再只记录日志后继续。合法终态回执重投幂等接受，冲突终态不覆盖首次结果。
数据库故障恢复后可重新提交同一回执，不能重新执行原动作；新 Agent 通过下述独立持久回执队列补传，旧 Agent 的流回执仍不具备此保证。

### 独立回执 ACK 协议

新增 `AgentService.ReportCommandResult(CommandResult) -> CommandResultAck`，沿用 Agent 身份验证与资产绑定。
必须携带非零 agent/command UUID；状态为 UNSPECIFIED 表示执行被 agent 停止或重启打断、结果未知，记为 unknown 交人核实，
已有终态时不覆盖。数据库存储完成或指令已有合法终态后才 ACK command_id，写失败不 ACK（Unavailable，agent 重传）；
库里没有这条指令或不属于当前 Agent 时返回 NotFound，agent 把该回执移入隔离区，不再重传（`grpcsvc/command_receipts.go`）。ACK 表示该指令已有持久终态，不表示本次提交覆盖了已有终态，也不是效果验证。
旧 Commands 双向流保留兼容；新 RPC 不发任何主机动作。测试覆盖写入故障、恢复、同一回执重传、错误 Agent 和未知状态。
Agent 执行完的结果落盘后，同时顺着 Commands 流回一份（旧 server 只认这条路，新 server 重复收到按终态幂等）；
旧 server 对新 RPC 返回 Unimplemented 时，本地回执视为已经走指令流送达并删除，不无限重传占满容量。
仍建议先升级 server 再升级 Agent：旧 server 拿不到执行中被打断的那类结果未知回执。

### Agent 持久回执队列（2026-10-19）

- 回执位于现有 server/hostname 作用域状态目录的 `receipts/`，共享状态目录的独占锁；记录携带注册 Agent UUID 和指令 UUID。执行前先写占位并同步，失败或容量满时不执行新动作。
- 最多 256 条记录，每条 protobuf 正文最多 1 MiB，另有 32 字节 SHA-256 校验；回执容量独立于事件缓存，最多约 256 MiB，写入临时文件另需最多约 1 MiB。目录/文件权限沿用 0700/0600（Unix），拒绝符号链接，不淘汰旧记录。
  损坏或认不出的回执文件移入 `receipts/quarantine/`（文件名前加毫秒时间戳）后照常启动，证据保留，采集不受影响（`receipts.rs`）。
- 执行结果写临时文件、同步后原子替换占位，再同步目录；完成落盘才进入上报队列。临时写盘失败时保留内存结果每 5 秒重试写入，不重新执行。进程在此时退出仍可能丢失内存结果，但占位保留为待核实。
- 独立循环使用新 RPC 上传，单次超时 15 秒，失败后 5 秒再试。逐条上报，单条失败不挡后面的。匹配的 command_id ACK 才删除结果；
  server 明确拒收（NotFound / PermissionDenied / InvalidArgument）的移入隔离区；server 换了注册身份后，旧身份的回执同样移入隔离区。
  重启、断线、不支持 RPC、错误 ACK 都不会触发动作重执行。
- 执行中重启留下的占位不会恢复执行，也不会报成成功或失败：下次启动时以「结果未知、未重执行」上报，server 记 unknown，
  需要人工结合指令记录和主机实际状态核实。占位因此不会永久占着 256 条名额。已经 ACK 并删除的记录不是永久防重账本，仍依赖服务端禁止重放旧命令，不能宣称 exactly-once。
- 健康快照增加可选 `receipts: {pending, incomplete}`，前者是持久终态待确认，后者包含仍在执行及中断后尚无持久结果的占位；不能据此判断某条动作失败。资产页展示两个数量，旧版本未上报显示未知。健康时间失效仍按原有过期提示处理。

本地测试覆盖容量耗尽、写入错误、损坏保留、身份不符、重复执行拒绝、未决占位恢复、回执重启恢复，以及真实 gRPC 下旧服务端/ACK 丢失/错误 ACK/成功确认。
用户确认目前没有 Windows 和真实身份目录测试环境；Windows 仅完成交叉 clippy，不能替代运行验收。
