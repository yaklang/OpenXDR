# 自治总控设计（草案）

> 状态：P1a（事实库、运维意图、研判与结案审计接入、总控页面）已实现；P1b（钥匙盘点、常设规矩）与 P2、P3 待做。

## 背景

OpenXDR 的自治由一组各管一段的子 Agent 组成：研判（triage）、运维巡检与跟进（findings work）、结案审计（closurereview）、
抑制评审（suppressreview）、误报统计（fpstats）、夜间维护（maintenance）等。每个子 Agent 只看得到自己手上的
一个事件或一条待办，遇到不知道的事就把自己标成「需人工」（`manual_business_decision`、`verify_source` 等）。

2026-11-10 到 11-12 的一轮人工清理暴露出，这些「需人工」大部分并不需要人：

| 卡住的问题 | 实际答案在哪 |
|---|---|
| uos-server 上「未登记」的 root 公钥是谁的 | 其中一把就是管理员自己的钥匙，钥匙在管理员的工作机上 |
| 10.1.1.32 枚举 PVE API 是谁 | 平台自己的事件里有完整的登录会话与命令 |
| node2「平台控制面配置被改」 | 部署文档与审计里有这次变更 |
| 10.1.1.3 运维键会话在做什么（判可疑的大头） | 是凯伊各会话的运维通道，但平台不知道某一次会话的目的 |
| dynamicdefend-v2 的备份单元是否授权 | 管理员口头确认过，没有结构化记录，每轮复查都重新判可疑 |

另一类问题是子模块之间没有协调：夜间维护在不需要重启时也切了数据库主节点、切完立刻下发指令、切换的几秒里两个节点同时执行，
三个毛病都来自「各模块只看局部、没有统一的执行者视角」。

## 目标与非目标

目标：
- 子 Agent 碰到「归属、授权、策略」类问题时，先从平台的权威事实里找答案，答得出就不打扰人。
- 管理员的每一次决定沉淀成结构化事实或常设规矩，同类问题不再问第二次。
- 真正需要人的问题，合并成每天一次、按主题归并的提问。
- 平台级操作（维护、切主、批量处置）有统一的单一执行者与跨模块的根因归并。

非目标：
- 不做一个「什么都管」的大 Agent。总控的主体是数据与规则，模型只做问题到查询的映射与归并。
- 不降低现有的独立审计：总控回答事实、执行已定的规矩，不批准自己或子 Agent 的提议。
- 身份是否本人、授权与否、不可逆操作（删快照、删数据、删账号）始终由人决定。

## 已有的零件

| 零件 | 现状 | 在总控里的位置 |
|---|---|---|
| 长期记忆（`memories`） | 自由文本，AI 与人工混写，研判按资产注入 | 保留为笔记；权威事实迁到事实库，人工记忆可一键转成事实 |
| 已知自动化（trusted sources） | 按登录身份（公钥指纹、来源网段、用户）放行 | 作为事实库里「通道」类事实的执行端，不变 |
| 修复策略（`repairpolicy`） | 按资产授予 `restart_failed_service`、`reclaim_disk` | 扩成常设规矩的动作目录 |
| 待办工作状态（findings work） | blocker 枚举，`manual_business_decision` 直接等人 | 改为先提问总控，答不了才进人工队列 |
| 抑制评审、结案审计 | 独立审计员 | 不变，总控不替代 |
| 飞书审批 | 命令与处置的审批卡片 | 承载每日合并提问 |

## 设计

### 一、事实库（P1）

事实是平台可以当作前提引用的结论，只收权威来源：管理员在控制台或 API 录入、平台自己的记录（发布、平台指令、维护、审批）、
部署流水线写入。日志与事件里的内容一律是待核验的数据，不能自动变成事实。

事实类型（第一批）：

| 类型 | 键 | 内容 |
|---|---|---|
| `key` | 公钥指纹 | 持有人、所在机器、用途、可登录范围 |
| `channel` | 来源地址或网段 | 归属（如 10.1.1.3 = 凯伊运维出口经 WireGuard）、谁会从这里来 |
| `asset_role` | 资产 | 角色与业务归属（如 raid-server-test = SoulRaid 红队测试机，扫描与渗透是业务） |
| `decision` | 主题 | 管理员的常设决定（如 PVE 宿主机不进夜间维护、存量备份不删） |
| `change` | 资产 + 时间窗 | 已授权的变更记录（谁、改了什么、依据） |

每条事实带：作用范围（组、资产）、来源与录入人、生效与到期时间、被引用次数。变更与删除留审计，
和抑制、已知自动化同一套治理。研判、巡检、结案审计的上下文里按涉及的资产、钥匙、来源地址注入命中的事实，
引用时带事实编号，审计员可核对。

### 二、运维意图登记（P1）

10.1.1.3 等运维通道上的会话占了可疑事件的大头，原因是平台只知道「谁登录了」，不知道「来干什么」。
运维方（凯伊各会话、同事）开始动生产前登记一句意图：

```
xdr intent start --hosts dynamicdefend-v2,raid-server-test --purpose "RBI 迁移自测" --ttl 2h
```

意图绑定登录身份（公钥指纹或来源地址），在有效期内覆盖列出的主机。研判碰到对应会话时，上下文里给出意图编号与目的；
行为落在意图范围内可以据此判良性。超出范围的主机、高危类别（凭据窃取、清痕、削弱防御、破坏）不因意图放行，照常研判，
与已知自动化的高危例外同一口径。意图到期自动失效，平台每天汇总「有意图的会话」与「没登记意图的运维会话」。

### 三、常设规矩（P1）

把管理员一次定下的处理原则结构化，命中即按规定的档位执行：

| 档位 | 含义 |
|---|---|
| `auto` | 直接执行，事后通知，留可回退记录 |
| `propose` | 生成提议，按现有审批流程 |
| `human` | 进人工提问队列 |

第一批规矩（来自 11-12 的人工清理，管理员确认后录入）：

| 规矩 | 档位 | 动作 |
|---|---|---|
| docker 未使用超过 7 天的镜像与匿名卷 | auto | 回收（扩展 `reclaim_disk`） |
| 包管理缓存、过大的 journal | auto | 清理 |
| 内存 4G 以下且无 swap 的主机 | propose | 加 2G swapfile 并写入 fstab |
| 旧备份 | auto | 只做无损压缩（校验通过才删原文件），从不删除 |
| 密码过期且从未登录的本地账号 | propose | 锁定 |
| 崩溃循环超过阈值的 systemd 服务 | propose | 停用并保留配置 |
| 指向不存在目标的密钥与连接配置 | propose | 移入封存目录 |
| 管理端口对内网全开 | propose | 按「只放行本机、容器网桥与管理主机」模板收口 |

`auto` 档的动作必须在修复能力目录里有固定模板、可回退，并受维护窗口与资产冷却约束。

### 四、提问协议（P2）

子 Agent 不再直接把自己标成「需人工」，而是调用 `ask_controller`：

```
{type: owner|authorization|policy|permission, subject: {kind: key|ip|asset|change, value}, evidence: [...]}
```

总控先做确定性查找（事实库、意图、平台记录、发布与审计），能答就返回结论与引用；答不了的问题进入人工队列，
按主题合并（同一把钥匙出现在五条待办里只问一次），每天一张飞书卡片推给管理员。管理员的回答写回事实库或常设规矩，
关联的待办与事件按新事实重新评估。

模型只用于把自由文本的问题映射成查询、把多个问题归并成一个，不负责给出事实结论。

### 五、协调层（P3）

- 根因归并：同一时间窗、同一变更、同一事实缺口引起的多条待办与事件归成一个根因，统一跟进。
- 单一执行者：维护、切主、批量处置等平台级操作要求单一执行者；状态写入带版本比对（已在维护中实现，
  见 `maintenance.State.Rev`），切主等会让租约短暂失效的操作期间，其他平台级操作暂停。
- 优先级与预算：按影响面排序子 Agent 的工作，避免同一根因占满研判与巡检预算。

## 前端

原则：只加一个新页面「总控」，其余能力嵌进已有页面；人要做的事集中到一处，别的页面只展示引用和入口。

### 新页面：总控（`/control`，放在「自动化」分组，菜单徽标显示待答问题数）

五个标签页：

| 标签 | 内容 |
|---|---|
| **概览** | 四个数字：待答问题、未认领钥匙、进行中意图、今日自动执行。下面一条时间线：总控今天答了什么（带引用的事实）、自动执行了什么（可回退）、升级给人什么 |
| **待答问题** | 按主题合并的问题卡片：问题一句话、影响多少条待办和事件（可点开）、证据（钥匙注释、命令行等攻击者可控原文只在这里显示）。作答表单按问题类型给结构化选项：归属 → 选持有人与用途；授权 → 授权/不授权、范围、到期；策略 → 选规矩与档位。默认「写入为事实」。另有「已答」历史 |
| **事实** | 按类型切换：钥匙、通道、资产角色、决定、变更。表格列：对象、内容、范围、来源（人工/平台/流水线）、录入人、生效与到期、被引用次数。管理员可新增、修改、停用；抽屉里看审计与哪些研判引用过它 |
| **钥匙** | 一行一把钥匙：指纹（短）、注释（灰色，标「仅提示」）、所在主机、账号、选项（`from=`/`command=`）、最近登录时间与来源、状态（在用/闲置/未认领/已认领）。管理员点「认领」填持有人、所在机器、用途；未认领的可「生成移除提议」，走现有审批 |
| **运维意图** | 进行中与历史：登记人（Token 或账号）、主机、用途类别、到期时间、匹配到的会话数、「事后」标记。「登记意图」按钮、每条可「提前结束」 |
| **常设规矩** | 规矩名、条件摘要、档位（管理员可切 auto/propose/human）、今日与 30 天命中、最近执行、是否因出错降级。抽屉里看执行记录与回退方式 |

### 嵌进已有页面

| 页面 | 加什么 |
|---|---|
| 资产列表 | 多选主机后出现「开始运维」，弹窗选用途类别与时长，提交即登记意图 |
| 资产详情 | 「事实与意图」卡片：资产角色、这台机器上的钥匙及状态、进行中的意图 |
| 事件详情、运维待办 | 研判与跟进结论旁显示「依据」标签（如「事实 #12：royal 钥匙 = 凯伊运维」「意图 #34：部署」），点开跳到总控对应条目；待办被总控挡下或已提问时显示「已向总控提问 #q」 |
| 总览 | 一张小卡：待答问题、未认领钥匙、今日自动执行，点进总控 |
| 长期记忆 | 人工记忆多一个「转为事实」操作 |
| 已知自动化 | 与通道事实互相链接 |

### 权限

viewer 只读；analyst 可以为登记在自己名下的通道登记意图；只有 admin 能作答、认领钥匙、增改事实与规矩。
所有写操作留审计，作答与认领不提供批量「全部同意」。

## 安全边界

- 总控只回答事实、执行已定的规矩，不扩大自身权限，不批准提议；结案审计、抑制评审保持独立。
- 事实只来自权威来源；日志、事件、模型输出不能变成事实。
- 身份是否本人、授权与否、不可逆操作始终进人工队列。
- `auto` 档动作全部审计、通知、可回退；同一规矩连续出错自动降级为 `propose`。
- 意图不能覆盖高危类别，也不能跨出登记的主机与时间窗。

## 分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| P1 | 事实库、运维意图登记、常设规矩（首批 8 条）、研判与巡检接入 | 来自已登记通道的运维会话不再产生可疑事件；`manual_business_decision` 待办减少一半以上；首批规矩命中后无人工介入完成 |
| P2 | 提问协议、人工问题合并、每日飞书卡片、回答写回 | 人工每天只收到一张合并提问；同类问题不出现第二次 |
| P3 | 根因归并、平台级单一执行者、优先级与预算 | 一次维护或变更引起的连锁问题归成一个根因；平台级操作无并发执行 |

## 定案（2026-11-12，凯伊与安琪儿分别从易用与安全两个角度讨论后确定）

### 意图登记：意图只用来解释行为，不用来放行

- **一个接口，两个入口**：后端只加 `POST /api/intents`。凯伊各会话用集成 Token（新增 scope `intents:write`），
  `curl` 一行或包成几行的脚本；同事在控制台资产列表勾选主机、点「开始运维」、选用途与时长。暂不做飞书指令。
- **登记凭据与 SSH 钥匙分开**：Token 按人或按工作机签发（Foghaven、Bifrost、zachary-dev 各一个，同事用自己的账号），
  不放在纳管主机上；只偷到 SSH 钥匙的人登记不了意图。Pi 不提供登记工具，与已知自动化同一口径。
- **绑定三项**：钥匙指纹 + 来源地址 + 主机列表。royal 钥匙同时在 10.1.1.3 和 10.1.1.161 上用，只绑指纹会互相放行。
  每个 Token 只能为事实库里登记在它名下的通道登记。主机数有上限、不许通配，TTL 最长 4 小时。
- **用途走固定目录**（部署、排障、迁移、巡检、测试……），研判只看类别；自由文本只给人看，不进模型的判断依据，防提示词注入。
- **放行上限**：意图只能把「行为类别与登记用途一致」的告警降为良性候选，仍须过独立结案审计。高危类别（凭据窃取、清痕、
  削弱防御、破坏、往 SSH 授权钥匙里加钥匙）、超出主机或时间窗的照常研判。
- **每次登记实时推送到飞书群**（谁的 Token、哪些主机、多久），被盗用登记的那一刻就能被看到。
- **忘了登记不阻塞操作**，照常研判，不会比现在更差。每日汇总列出「没登记意图的运维会话」。允许开始后 2 小时内补登，
  补登的意图标为「事后」，研判只作参考，不能单凭它判良性。
- 共用钥匙下多个凯伊会话同时登记，平台分不出具体会话，生效范围取各次登记的并集。根治办法见下面「附带决定」。

### 钥匙盘点：agent 上报观测，管理员确认归属

- **收集**：agent 以 root 读取，覆盖 `sshd -T` 解析出的 `AuthorizedKeysFile` 与 `AuthorizedKeysCommand`、所有用户家目录、
  `/etc/ssh/authorized_keys.d`。只上报指纹（与 `login_session.key_fp` 同为 SHA256 格式）、注释、账号与选项（`from=`、
  `command=`、`cert-authority` 等），不报公钥原文。启动时报一次，之后复用现有 fswatch，文件变了再报，不另做轮询。
- **观测不是事实**：盘点结果和实际登录记录交叉比对，标出「在用 / 闲置（90 天无登录）」，平台汇总成一页钥匙清单，
  在用的排前面。没装 agent 的机器（PVE、gitlab）第一期不管。
- **认领**：只有管理员能在控制台确认持有人与用途，确认后才成为 `key` 事实；AI 只能起草建议，不能确认。
  公钥注释（如 `kei@foghaven`）只作提示，不作依据，注释谁都能随便写。
- **新出现的钥匙**：照常告警，附上写入它的登录会话，平台生成一条移除提议，**从不自动删除**（自动删可能把管理员自己锁在门外）；
  清单里标「未认领」，P2 起进合并提问。永远不自动信任新钥匙；闲置钥匙删不删由人决定。

### 飞书审批应用配置前：群里通知，控制台作答

- 每天至多一条群消息：问题数、按主题一行摘要、控制台「待答问题」页链接。当天没问题就不发。问题再多也合成一条。
- **回答只在控制台**：登录的管理员作答，在同一事务里写回事实库或常设规矩并留审计。链接不带任何能直接作答的令牌。
- 群里不止管理员一人，消息只放主题与数量，钥匙注释、命令行这类攻击者可控的原文只在控制台看。
- 应用配置好以后，影响小的问题可以做成私聊卡片按钮，复用现有的 open_id 绑定、nonce 与 message_id 校验；
  认领钥匙、登记通道这类扩大信任的回答仍然只在控制台。

### 附带决定

- **已修**：已知自动化的高危例外漏了往 SSH 授权钥匙里加钥匙（T1098.004）。可信来源被盗用时这是留后门最直接的一步，
  已列入高危例外（只收这一项持久化技术，装服务、写 cron 是运维日常，不收）。
- **建议管理员决定**：royal 运维钥匙由多台机器、多个会话共用，平台从指纹上永远分不清是谁（11-10 termix 解密数据库查不到人
  就是这个原因）。各台工作机换成各自的钥匙，比任何意图机制都管用。
