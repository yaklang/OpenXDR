# 自主响应与自身防护设计

起因同 [跨主机攻击的关联与升级设计](attack-campaign-design.md)。2026-11-02 跳板开始喷洒，11-03 打进生产库，
11-03 10:11 每日巡检已经把入侵写成「紧急」，但推送暂停，三天没人处置。攻击方是自动化的，几小时写了十几个脚本，
比人工响应快得多。

结论有两条：

- 平台要自己闭环。人在事后审计、推翻决定，不在关键路径上。通知还要发，但内容是「已经做了什么」，不是「请来处理」。
- 能自主动手的平台本身就是最值钱的目标，自身防护和自主响应要一起设计。

## 现状

| 项 | 现状 | 问题 |
|---|---|---|
| 开关 | 生产只开了 `RESPONSE_ENABLED`，`AUTO_RESPONSE_ENABLED` 没开 | 实际上没有自主响应 |
| 触发 | 只有 AI 研判结论 malicious 且置信度 ≥ 90（`response/auto.go`） | 分钟级；模型不可用时完全不响应 |
| 动作 | 只有隔离整台主机 | agent 支持 9 种处置，自动响应只用了最重的一种 |
| 目标 | incident 里所有涉事资产，**包括受害者** | 这次如果开着，会隔离 node1，自己把生产停掉 |
| 粒度 | 主机 | 攻击者在 uos-server 的靶场容器里，隔离主机会把整个平台一起断掉 |
| 界面 | incident 详情里的 `ResponsePanel` | 看不到平台做过什么、什么还在生效，也没有集中撤销 |
| 指令通道 | agent 执行收到的任何指令；跨节点经 NATS，6222 只靠一个共享密码 | 拿到路由密码就能给全网发 root 命令（已由指令签名修复，见下文） |

## 设计

### 一、两条触发路径

**快路径：确定性信号，秒级，不经过模型。** 告警落库后同步判定，命中就进入处置引擎：

| 信号 | 依据 | 现状 |
|---|---|---|
| 内网横向喷洒 | `xdr:internal-lateral-spray`（P0 已上线） | 有 |
| 数据库进程拉起 shell | postgres / mysqld / redis-server / sqlservr 的子进程是 sh / bash / python 等（`COPY FROM PROGRAM`、UDF） | **缺规则**，要补 |
| 容器内试探逃逸 | 容器里访问 docker.sock、挂载宿主机设备、nsenter、写 cgroup release_agent | 部分 SigmaHQ 规则覆盖，需梳理 |
| 爆破得手 | `xdr:bruteforce-success` | 有 |
| 高置信情报命中 | 情报库 C2 / 恶意 IP 的出站连接 | 有 |

信号清单写在代码里，不由 AI 或配置临时扩充；新增信号要像新规则一样回测误报。

**慢路径：AI 研判。** 保留现有的 malicious ≥ 90 钩子，但目标选择和动作强度改走下面同一套引擎，不再直接隔离全部涉事主机。

### 二、按角色选目标

这是这次最大的教训：**遏制攻击来源，对受害者只做外科手术式的处置。**

| 角色 | 怎么认 | 处置 |
|---|---|---|
| 来源主机 | `lateral_evidence` 的 `src_asset`；受害方事件里 `authfields.PeerIP` 落在纳管主机上 | 按区域等级遏制（见下） |
| 来源容器 | 来源主机在窗口内连向受害地址的出站网络事件，取事件的 `container` | 隔离这个容器，不动宿主机 |
| 受害主机 | 告警所在资产 | 结束恶意进程树（如 postgres 下的 sh），封锁来源地址；**永远不隔离整机** |

来源容器能认出来，是因为 agent 的 eBPF 网络采集带进程与容器归属：跳板容器的流量在受害方看来源地址是宿主机 IP（Docker NAT），
但宿主机上的 agent 看得到是哪个容器发起的。

### 三、动作强度按区域等级

在区域（`Zone`）上加一个处置等级字段，资产可以单独覆盖。未指定时为「生产」：

| 等级 | 适用 | 来源侧 | 受害侧 |
|---|---|---|---|
| 实验 | 靶场、CTF、AI 实验机、测试 VM | 隔离容器；认不出容器就隔离主机 | 结束进程 + 封锁来源 |
| 生产 | 默认 | 隔离容器；认不出容器就封锁它与其他纳管主机的通信，不隔离主机 | 结束进程 + 封锁来源 |
| 核心 | OpenXDR 自身节点、数据库、网关、DNS | 只封锁来源，不隔离 | 只结束确认恶意的进程、封锁来源 |

运行 OpenXDR server 的资产自动归入核心，不依赖人工配置。

### 四、遏制租约

每次自动处置都是一条**租约**，记在新表 `containments` 里：

- 字段：资产、动作、目标（容器 ID / 地址 / 进程）、触发信号、关联 incident、下发的指令、生效时间、到期时间、状态、解除人与原因。
- 默认有效期 24 小时。同一来源在租约期内又有新证据，就自动续期。
- 到期前由 AI 复核：攻击是否还在继续、来源是否已清理干净。复核结论只能是「解除」或「续期」，**不会自动升级成更重的动作**。
  复核出错按续期处理。
- 人可以随时解除，解除会下发反向指令并记审计。

到期自动解除只适用于封锁和容器隔离。结束进程不可逆，只记录，不进租约。

### 五、新能力：容器隔离

agent 新增 `ISOLATE_CONTAINER` / `UNISOLATE_CONTAINER`，目标是容器 ID：

- Linux：按 cgroup 找到容器里的进程，进它的网络命名空间（`/proc/<pid>/ns/net`），在里面建一张独立的 nftables 表，丢弃全部流量。
  宿主机和其他容器都不受影响。
- 只支持 docker / containerd / LXC 这类有独立网络命名空间的容器。`network_mode: host` 的容器拒绝执行并说明原因。
- 容器重启会换网络命名空间，隔离随之失效。租约期内 agent 检测到同一容器 ID 重新出现时，自动重新隔离并回报。

### 六、保险丝

- **熔断**：一小时内全局自动处置超过 N 次（默认 10），或单组超过纳管主机数的 20%，就停止自动处置，只记录待执行的决定，
  等组管理员恢复。宁可漏处置，也不能让一个误报信号把全网关掉。
- **幂等**：同一信号、同一目标只处置一次，ID 由信号与目标派生（沿用 `auto-isolate` 的做法）。
- **全程审计**：动了、没动、被熔断挡住，都要写清「为什么」。
- **指令签名**：见下文。签名是自主响应的前提，否则就是在给攻击者造武器。

### 七、页面：自主响应

控制台新增一级菜单「自主响应」：

- **当前遏制**：生效中的租约、剩余时间、触发证据，可以一键解除。
- **决策记录**：每次判定的时间线，包括被跳过和被熔断的，点进去能看到信号、角色认定和选择的动作。
- **策略**：信号 × 等级 → 动作的矩阵。第一版只读，展示代码里的策略。
- **熔断状态**：当前计数与阈值，组管理员可以在这里恢复。

通知改成事后报告：「已自动隔离 uos-server 上的容器 range_c11_comp1_t2，原因是 60 分钟内对 6 台主机喷洒 SSH」。

## 自身防护

### 已完成：端到端指令签名（PR #32）

- 每条指令都装进签名信封：绑定目标 agent、一小时有效，用 `COMMAND_SIGNING_KEY_FILE` 的 Ed25519 私钥签名。
- agent 首次注册时固定公钥，只执行验签通过的信封里的指令。
- 数据库、跨节点 NATS 或单条投递链路被人摸到，都伪造不出 agent 肯执行的指令。

剩下的缺口：server 节点本身被拿下时，节点上有私钥，也能通过自动升级分发安装包。后者要用离线密钥给安装包签名，单列一项。

### 待做

1. **控制面网络收口进部署代码**：5432 / 8008 / 2379 / 6222 只对固定的对端开放，写进 `deploy/ha`，替代 11-04 手工加的
   KEI-DBGUARD / KEI-ETCDGUARD。PR #31 一并处理。
2. **把 OpenXDR 自身当核心资产监控**：数据库进程拉起 shell、pg_hba 或 Patroni 配置被改、陌生地址访问 etcd、
   告警表或审计表被批量删除、核心节点 agent 掉线，都走快路径。
3. **审计防篡改**：审计做成哈希链，定期把链尾写到集群外的见证节点（jumpbox）。删记录能被发现。
4. **安装包签名**：自动升级只接受离线私钥签过的安装包，与指令签名分开两把钥匙。
