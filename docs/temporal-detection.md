# 时序检测实现约定（开发中）

`server/internal/temporal` 当前包含规则快照、确定性求值及 PostgreSQL 候选/命中存储，**已接入 Processor，并可通过 TEMPORAL_RULES_PATH 显式启用**。
下列 YAML 应放入独立的时序规则目录；不要放进现有 Sigma `rules/` 目录。
现有 Sigma 单事件引擎仍拒绝未实现的聚合条件。

## 规则格式

计数规则引用一个已加载的基础规则：

```yaml
id: auth-failure-burst
kind: event_count
within: 10m
rules: [authentication-failure-rule-id]
threshold: 5
level: high
```

严格序列按基础规则 ID 顺序列出步骤：

```yaml
id: discovery-then-persistence
kind: sequence
within: 15m
rules: [discovery-rule-id, persistence-rule-id]
```

不论先后的共现（`temporal`，取名同 Sigma correlation 的 temporal 类型）列出 2 至 8 条**互不相同**的基础规则，
窗口内每条各由一个不同事件命中即成立：

```yaml
id: download-pipe-shell
kind: temporal
within: 5s
rules: [download-tool-signal-id, shell-stdin-signal-id]
```

可选 `group_by` 决定关联实体：`asset`（默认，同组同资产）、`account`（同组同账号，跨同组多台主机累计）
或 `asset_source_ip`（同组同资产同来源 IP，不同来源各自计数，不凑同一个阈值）：

```yaml
id: account-auth-failure-burst
kind: event_count
group_by: account
min_assets: 2
within: 10m
rules: [authentication-failure-rule-id]
threshold: 5
```

`event_count` 可选 `min_assets`（1–100，默认 1）：窗口内参与计数的事件须来自至少 N 台不同资产。
它只对 `group_by: account` 有意义；`group_by: asset` / `asset_source_ip` 时写大于 1 的值、用于 `sequence`、超出范围或大于 `threshold` 都拒绝加载。
账号规则设 `min_assets: 2` 可避免单机多次失败同时触发主机规则与账号规则的重复告警。

加载拒绝未知字段、未知 `group_by` 取值、非法 `min_assets`、多 YAML 文档、不存在的基础规则、与基础规则冲突的 ID 和不支持的类型。
窗口限定为 1 秒至 24 小时；计数阈值为 2 至 10000；序列为 2 至 8 步，不允许 threshold；`temporal` 为 2 至 8 条不重复的规则，
不允许 threshold 与 `min_assets`（同一规则多次出现用 `event_count`）。
`level` 支持 informational、low、medium、high、critical，省略时默认 medium；未知值拒绝加载，等级跟随同一快照传入告警。
格式是 OpenXDR 自有时序规则契约，不宣称兼容 Sigma correlation 标准。

### 信号规则

时序步骤引用的基础规则默认是普通 Sigma 规则，每次命中都单独告警。只在链路里才有意义、单独看全是噪声的动作
（`curl` 启动、读 stdin 的 shell、每次成功登录）写成**信号规则**：Sigma 规则顶层加 OpenXDR 扩展字段
`openxdr_signal: true`，`level` 必须为 `informational`，放在 `rules/signals/`（目录只是约定，语义只看字段；
基础规则目录递归加载，随 `RULES_PATH` 一起发布）。字段只接受 `true`，写 `false`、字符串或级别不是 informational 都拒绝加载。
字段随原文进规则版本哈希与归档，从归档恢复也还是信号规则。

- `sigma.Engine.Evaluate` 不返回信号规则，所有出告警的路径（ingest、旧 gRPC 直写、sensor、syslog、单事件回测与 detectcheck 的命中判定）
  都看不到它；只有 `EvaluateSignals` 返回。未配置 `TEMPORAL_RULES_PATH` 时信号规则完全不生效。
- `Snapshot.CandidateRules` 把告警规则命中与信号规则命中合在一起，只保留被时序规则引用的 ID 写入候选；
  没有被任何时序规则引用的信号不落候选，候选量只随实际用到的信号增长。
- 信号命中不产生告警，也就不进去重、关联、研判与通知；只有它参与的时序规则命中才出告警（终点可以是信号事件）。
- 规则页给信号规则打「时序信号」标记，ATT&CK 覆盖矩阵不计信号规则。

## 求值语义

- 输入是带稳定事件 ID、事件时间、可信归组/实体、基础规则命中 ID 的候选事件。
  归组必须由后端授权上下文提供；不能直接采纳原始日志或模型自报的组。
- 同一 ID 重投只计一次。同 ID 的时间、归属或基础规则命中不同则拒绝求值，避免接受冲突副本。
- 关联只发生在相同 `(Group, Entity)` 内；缺失身份、时间或归属时拒绝。
  `group_by: asset` 的实体是资产 ID；`group_by: account` 的实体是 `account:<规范化用户名>`，
  用户名只取事件 `username` 列（入库信封字段），规范化为去首尾空白、转小写，不做 `DOMAIN\user`、UPN 等格式互认，
  也不从原文或模型输出推断账号。`username` 为空的事件不参与账号规则，计入 `no_account` 缺口；资产维度规则照常。
  `group_by: asset_source_ip` 的实体是 `asset-source-ip:<资产 ID>|<规范化 IP>`，来源只取原文 `src_endpoint.ip`，
  缺这个字段时只对 sshd 失败日志按严格格式解析 `from <IP> port <端口>`；IPv4 映射的 IPv6 归成 IPv4，
  主机名、带端口、未指定和组播地址都不算来源。syslog 报文的传输对端（可能是日志中转）不当作来源。
  取不到来源的事件不参与这一维度，计入 `no_source_ip` 缺口；其他维度照常。
- 窗口包含两端，按 `[终点时间−within, 终点时间]` 取候选。
- 计数是不同事件的数量。同时间戳的不同 ID 仍可计数；按时间、UUID 排序确定终点。
  只在条件越过的那一刻产生命中：条件是窗口内计数达到 `threshold` 且不同资产数达到 `min_assets`，
  终点之前同窗口的事件已满足条件就不是越过的那一刻。持续爆破时窗口一直满足条件，不逐条出命中，
  回落到不满足再越过才有下一次。否则每个终点都绑定告警、证据事件永不过期，写库次数随窗口线性增长。
  `min_assets` 为 1 时即窗口内计数恰好达到阈值的终点。设了 `min_assets` 时，可能计数早已达到阈值、
  第二台资产的事件出现时才越过，此时证据是窗口内全部计数事件（可能多于 threshold 条）。
  迟到事件补上第二台资产时，命中落在它按事件时间越过的终点上，之后的终点前序已满足，不再重复。
  新事件只重新求值它之后（含同一时刻）的终点；更早的终点已在当时求值落库（`temporal/evaluate.go`、`postgres.go`）。
- 序列每一步必须使用不同且严格晚于前一步的事件。同时间戳不证明先后，不能跨步骤使用。
  同一个基础规则可重复出现在步骤中，但必须由不同时间的事件分别满足。
- `temporal` 不要求先后：窗口 `[终点时间−within, 终点时间]` 内，每条引用规则各分配一个不同事件（同一事件命中多条规则时按二分图匹配分配，
  不会一条占两条规则），同时间戳也算。终点可以是命中任一引用规则的事件；与计数一样只在条件越过的那一刻出命中——
  终点之前的同窗口事件已能凑齐就不是越过，持续出现不重复出命中。证据是凑齐时选中的事件（每条规则一个）按时间、UUID 排序，
  终点必然在内且在最后；每条规则只取窗口内最早的若干候选（规则条数个），结果只取决于事件时间顺序。
  它解决兄弟进程几乎同时 exec、采集到的先后不可信的问题（如管道 `curl … | bash`），严格序列在这里会随机漏报。
- 每个命中返回终点事件 ID、时间、归属及完整有序证据 ID。候选按时间/UUID 排序后选取首个满足条件的证据链，
  不依赖传入顺序；迟到输入补全窗口后重算仍以同一终点作为幂等依据。
- 单次超过 10000 个候选直接报错，不截断成看似成功的阴性结果。此上限不是生产吞吐承诺。

## 完整规则快照

`LoadSnapshot(baseDir, temporalDir)` 将基础规则和时序规则一起加载。不同于原单事件引擎允许跳过坏规则的路径，
该入口遇到任一加载错误或重复 ID 会拒绝整批；时序引用只能指向这批已编译基础规则。
版本哈希包含两类规则实际参与编译的内容，不依赖目录路径和枚举顺序。返回的命中包含快照版本。

`Store.Reload` 构造完成后原子发布；失败保留旧快照。处理一次事件应只取得一次 `Current()`，
随后用同一快照完成基础匹配和时序求值。旧快照可继续使用，基础命中的可见元数据返回副本。
第一次尚未成功加载时 `Current()` 为 nil，调用方必须显式处理，不能伪装为成功的空规则集。

配置 `TEMPORAL_RULES_PATH` 后，基础匹配和规则展示统一使用完整快照，不再单独启动 Sigma Watch。
`RULES_RELOAD_SECONDS` 控制整体重载，0 表示关闭重载；首次加载失败拒绝启动，后续失败保留旧快照并记录错误。

### 不可变版本目录发布

原地逐文件修改不能保证整个目录来自同一次发布，生产应使用不可变版本目录加符号链接：

```text
/opt/openxdr/temporal-rules/
  v-20261020-1/        # 一次发布一个新目录，写完不再改动
    linux-auth-burst.yml
    SHA256SUMS         # 最后写：cd v-20261020-1 && sha256sum *.yml > SHA256SUMS
  current -> v-20261020-1
```

`TEMPORAL_RULES_PATH` 指向 `current`。每次加载先把 `RULES_PATH` 与 `TEMPORAL_RULES_PATH` 各解析一次成实际目录，
再整批读取，同一次加载不会混读新旧目录的文件。发布时写完新目录和清单后原子替换链接：
`ln -s v-<新版本> current.tmp && mv -T current.tmp current`；下个重载周期整体切换，失败保留旧快照。

`TEMPORAL_RULES_PATH` 本身是符号链接时，目标目录必须带 `SHA256SUMS`（`sha256sum` 文本格式，相对路径，只列 `.yml`/`.yaml`）。
清单缺失、格式错、列出的文件不存在、摘要不符或目录里有未列出的规则文件，整批拒绝：首次加载拒绝启动，
后续重载保留旧快照并记录错误。普通目录（非链接，如镜像自带的 `/opt/openxdr/temporal-rules`）不强制清单，
若带了清单同样逐一核对。规则版本哈希只取内容，不含目录名，回滚到内容相同的旧目录得到同一版本。
基础规则目录不要求清单；基础与时序规则需成套发布，时序规则引用缺失的基础规则时整批拒绝。

## 已使用版本归档

首次处理该快照的有效候选时，实际编译的基础规则及时序规则原文存入 `temporal_rule_snapshots`，
以版本哈希唯一保存，与候选处理同事务提交。已有版本不重复传输整份归档；回滚不会留下本事务首次写入的归档。
归档来自内存中已编译内容，不重新读当前目录，因此文件后来改动不会替换历史规则。

`RestoreArchive` 支持格式 1，重新编译原文并校验版本哈希；拒绝损坏内容、不支持格式、未知字段及尾随文档。
当前测试验证在本版本引擎下能重现结果；未来编译语义变化必须处理格式兼容，不能仅凭原文相同声称跨引擎版本语义一致。
归档不通过公开规则列表接口分发，也不会自动回填以前未记录的版本。无引用的旧归档由 janitor 清理（见「无引用归档清理」），当前规则页仍展示最新版本元数据。

### 历史规则查询

`GET /api/temporal-rule-snapshots` 列出最近使用过的版本，`GET /api/temporal-rule-snapshots/{revision}?rule=<ID>`
按版本哈希取当时的时序规则原文、元数据（类型、`group_by`、窗口、阈值、`min_assets`、等级）及其引用的基础规则原文，参数见 [REST API](api.md#事件与告警)。
只有全局 admin / analyst 可读，角色每次从库里取，降权立即生效；viewer 返回 403。

告警本身不存版本：时序告警经 `temporal_detections.alert_id` 关联命中记录，命中记录带版本（去重指纹含版本，
一条告警只对应一个版本）。`?alertId=` 只返回调用者能看到的告警（全局 admin，或告警资产所在组的成员）所绑定的版本。
事件详情的告警表展开行里，时序告警有「查看当时规则」入口；单事件告警、加 `alert_id` 列之前的旧告警没有关联，不显示入口。

展示用 `ViewArchive`：按原文重算版本哈希并与库中版本核对，只编译时序规则、不编译基础规则，
因此不受基础规则引擎后续语义变化影响；归档被改动或格式不支持时返回 500 拒绝展示，不把不可信内容当成当时的规则。
它只回答「当时规则原文是什么」，能否在当前引擎下重现结果仍由 `RestoreArchive` 负责。

## PostgreSQL 状态入口

`Snapshot.Observe(ctx, tx, eventID, baseHits)` 读取已入库事件及资产当前归组，
在资产共享行锁下固定归属，再按资产/快照获取事务锁。Processor 只将时序规则实际引用的基础命中（含信号规则命中）传入候选存储，
未命中事件、无关基础规则及未被引用的信号不占候选窗口；它们仍正常入库，告警规则照常产生单事件告警。候选存入 `temporal_candidates`；
回查本次事件时间前后最大窗口，重新评估可能受迟到事件影响的终点。
每个新命中插入 `temporal_detections` 并保留完整有序证据 ID；唯一键绑定快照版本、规则和终点。
同版本同事件的重投内容不一致时拒绝，未知基础命中也拒绝。持久处理路径的候选超限记录为检测缺口，不返回部分结果。

资产 group_id 改变时，数据库触发器删除该资产候选，防止 A→B→A 重新复用早先 A 的序列。
这只重置候选，不重新生成已经消费的命中；账号维度同样受此约束——资产换组后，它此前的事件不再计入任何组的账号窗口。
候选额外保存规范化账号（`account` 列，无用户名为 NULL），账号维度按 `(版本, 组, 账号)` 回查窗口。
处理时先取资产锁、再取 `(版本, 组, 账号)` 锁：不同资产落在不同队列分片也会在同一账号上串行，
后提交的事务一定看到先提交的候选；每个事务至多持有一个资产锁和一个账号锁，顺序固定，不会成环。
账号维度命中的告警绑定终点事件及其资产，去重指纹使用账号实体，同组同账号在去重窗口内合并为一条告警。
候选另存来源实体（`source_entity` 列，取不到来源为 NULL），来源维度按 `(版本, 组, 来源实体)` 回查窗口。
来源维度只管计数口径：命中照常按来源实体各自记入 `temporal_detections`，但告警去重指纹用资产 ID，
同一主机被多个来源各自打满阈值时在去重窗口内合并为一条告警、计数累加，告警说明记首个来源 IP；
否则 50 个来源同时爆破一台主机会出 50 条同级告警。
没有资产或没有组时在 `Observation.Skipped` 显式记 `unscoped`，调用方需要记录该覆盖缺口。

此入口要求调用方只处理本事务首次成功插入的事件，并与告警写入共用事务；重投已入库事件不能在换组后重新解释归属。
目前 Processor 设置 Temporal Store 后，会在首次事件插入的同一事务中调用 Observe 并生成时序告警；
告警绑定终点事件，抑制和平台指令归属使用终点原文，去重指纹额外包含快照版本及组。告警等级来自规则 level；
规则页和告警标题查询使用同一 Catalog，规则页展示类型、窗口、计数阈值和作者。没有有效快照时处理失败，不退回空规则成功。覆盖缺口统一计入 `openxdr_temporal_skipped_total{reason}`，见下文「覆盖缺口」。
未设置 `TEMPORAL_RULES_PATH` 时保持原单事件模式。容器需通过 Compose override 把独立规则目录只读挂载进去，环境变量填写对应容器内路径；现有模板仅透传变量，不自动创建规则或挂载任意主机目录。

每次新命中的前序事件写入 `temporal_evidence` 外键关系，命中记录关联实际生成或合并到的告警。
清理器同时排除直接告警引用、时序前序证据和合并告警的后续终点。数据库延迟外键阻止并发事务提交删除仍被使用的证据。
告警删除后级联释放其命中与证据关系，过期原文重新进入清理范围；被抑制的命中不绑定告警，可随过期终点清理释放证据。
这不是永久保留：原文跟随告警生命周期。新约束不恢复此前已经丢失的历史证据，也尚未回填旧版命中记录。

## 尚需完成的验收与边界

1. 规则发布已支持不可变版本目录加符号链接切换（见上文），单测覆盖切换、半写入拒绝与失败保留旧快照；
   真实服务中的发布/重载仍待实机验收。
2. 候选已按「最大窗口 + 迟到余量」单活清理（见「候选过期清理」）；告警证据仍跟随告警生命周期，可能长期保留。
3. 迟到超出余量、候选超限、未分组、无用户名四类覆盖缺口均有计数，前两类另写缺口记录（见「覆盖缺口」）。
4. 历史规则原文已归档并提供授权查询接口与告警「查看当时规则」入口；规则页仍只展示最新版本元数据，告警标题按最新版本取；无引用旧归档已接入保留任务清理。
5. 真实数据库并发、回滚、重启、乱序/迟到和组隔离回放；处理旧版本升级的历史告警重复问题。

当前确定性核心单测不能替代以上集成验收。

## 仓库实验规则与回放

[`temporal-rules/`](../temporal-rules/README.md) 提供 22 条规则：认证失败计数（主机 / 账号）、爆破后侦察（含「失败 → 成功 → 侦察」严格形态）、脚本内管道下载执行、Windows 侦察集中、
下载执行后持久化、凭据读取后打包/外传/外联、防御削弱后可疑执行，以及 Windows 对应链路，需显式配置后启用。
各条的窗口、阈值理由与已知误报写在该目录 README。规则仅作时间关联，不推断跨账号身份或进程因果链；
窗口都不超过 15 分钟，避免放大候选回查范围（见「候选容量缺口」）。
[`validation/temporal/`](../validation/temporal/README.md) 包含 81 个原文回放用例（每条规则至少一个正例与一个运维良性对照），
并配套最早三条规则与管道下载执行（两步都是信号规则，另核对信号不单独告警）的真实 PostgreSQL 迟到/重投/处理器恢复测试；不声称完成实机或生产误报率验收。

## 回测

新时序规则上线前用 `server/cmd/backtest` 在生产只读副本上回测命中量（在 `server/` 下）：

```sh
DATABASE_URL=<只读副本> TEMPORAL_RULES_PATH=../temporal-rules \
  go run ./cmd/backtest -from 2026-10-01T00:00:00Z -to 2026-10-04T00:00:00Z [-samples 3] ../rules
```

设了 `TEMPORAL_RULES_PATH` 即进入时序模式，位置参数是配套的基础规则目录（同线上 `RULES_PATH`），两者按 `LoadSnapshot`
整批严格加载，任一错误直接退出；`-from`/`-to` 为 RFC3339，缺省为最近 `-days` 天到现在。只读取时序规则引用的基础规则
关心的事件类别，按小时分段、每段一个 `READ ONLY` 事务按 `(ts, id)` 排序读取（连到主库也写不进去），副本冲突取消的段整段重试，
整段提交成功后才喂入回放状态（副本冲突也可能在提交时才报，先喂再提交会让重试的段重复喂入、报「未按 (时间, ID) 递增」），不会重复计数。输出版本哈希、每条时序规则的命中次数、维度、按资产（主机名）/ 账号的分布（前 10）、
样例证据事件 ID，以及 `unscoped` / `no_account` / `no_source_ip` / `candidate_limit` 覆盖缺口计数。
另报告每条被引用的基础规则（信号规则单独标出）贡献的候选数与每天均值，以及资产 / 账号 / 主机+来源 IP 维度单个实体窗口里的候选峰值：
线上 Observe 回查 `[t − 最大窗口, t + 最大窗口]`，最坏约为峰值的两倍，用它对照 10000 的上限判断新信号会不会撑出 `candidate_limit`。
不设 `TEMPORAL_RULES_PATH` 的单事件回测也统计信号规则的命中（标「信号，不告警」），用来估它被引用后的候选量。

回放与线上 Observe 用同一快照、同一实体口径，终点只在它按排序到达时求值一次，等价于全部事件按时到达后的线上结果。差异：
归组取资产**当前**的组（历史归组不可知，换过组的资产会被按新组统计）；不模拟到达顺序、迟到余量与候选清理，
因此不会出现 `late`；候选上限按回放到终点时已见的窗口判断。平台指令拉起的事件与单事件回测一样不计。

## 覆盖缺口

时序检测不能静默跳过事件。下列情况事件本身照常入库、照常出单事件告警，只是没有（完整地）参与时序求值，
提交成功后按原因逐项增加 `openxdr_temporal_skipped_total{reason}`（同一事件同一原因只计一次，重投不重复计数）：

| reason | 触发条件 | 缺口记录 |
|---|---|---|
| `unscoped` | 事件没有资产，或资产未分组；所有维度都不求值 | 无（没有组就没有可授权展示的归属） |
| `no_account` | 事件命中了账号维度规则引用的基础规则，但 `username` 为空；资产维度照常 | 无（规则适用性问题，不是窗口残缺） |
| `no_source_ip` | 事件命中了来源维度规则引用的基础规则，但取不到可信来源 IP；其他维度照常 | 无（同上） |
| `candidate_limit` | 某个维度完整查询窗口超过 10000 条候选，见下节 | `temporal_evaluation_gaps`，两个维度都超限只记一条 |
| `late` | 事件时间早于数据库 `now() - LateGrace`（2 小时），窗口内候选可能已被清理 | `temporal_evaluation_gaps`，候选数量下限为 0，不写候选 |

监控需同时关注这四类计数：事件入库与队列确认不代表时序检测完成。`late` 常见于 agent 长时间离线后补传缓冲，
这类事件不会在补传后自动补检。缺口记录随原始事件/资产删除级联清理，见「缺口查询接口」。

## 候选过期清理

配置 `TEMPORAL_RULES_PATH` 后，集群单活任务 `temporal-candidates`（`cluster.RunLeader`）每 5 分钟按批（每批 1 万条，删满继续）
删除不会再被读取的候选，与 `RETENTION_DAYS` 无关：

- 当前快照版本：事件时间早于 `now() - 最大窗口 - LateGrace - 10 分钟`。更早的迟到事件已按 `late` 跳过，
  余量内的迟到事件回查窗口下界不早于该时间；10 分钟覆盖处理事务从开始到读窗口的耗时（`now()` 为事务开始时间）。
- 其他版本（重载过程中可能仍有节点在用）：按规则允许的最大窗口 24 小时计，即早于 `now() - 24h - LateGrace - 10 分钟`。

判断都用数据库时间，与 Observe 的迟到判断同一时钟。候选不被告警、命中或 `temporal_evidence` 引用，
删除候选不影响已落库命中、证据关系与原始事件；原始事件仍由 janitor 按证据关系决定是否清理。
旧版本候选清空后，其归档在没有命中与缺口引用时由 janitor 的 `PruneArchives` 释放。

## 候选容量缺口

生产 Observe 在完整查询窗口 `[事件时间 - 最大窗口, 事件时间 + 最大窗口]` 超过 10000 条候选时，
不在截断数据上求值。它将 `candidate_limit` 写入 `temporal_evaluation_gaps`，记录规则版本、触发事件、
资产、当时组、窗口上下界和候选数量下限（10001 不是精确总数）。原始事件、候选、基础告警与缺口同事务提交。
写缺口失败仍回滚并由队列重试；容量缺口成功落库后允许队列继续处理，避免 `MaxAckPending(1)` 分片永久卡住。

提交后增加 `openxdr_temporal_skipped_total{reason="candidate_limit"}`，重投不会重复增加。
事件入库/队列确认不代表所有检测完成，监控必须同时关注该缺口指标。
纯内核 Evaluate 仍拒绝超出上限的输入，不能用它直接做截断检测。

新事件窗口降至上限内后可继续求值，但旧缺口不自动消失，也没有将重投作为补检。
当前缺口跟随原始事件/资产删除级联清理，因此不是永久覆盖审计；清理前应导出需要留存的覆盖记录。
目前提供只读查询接口与资产详情缺口界面，尚无授权补检入口。

### 缺口查询接口

`GET /api/temporal-gaps?assetId=<UUID>` 返回 `{items, truncated}`。必须指定资产；
`from`/`to` 为 RFC3339 时间，筛选的是缺口记录创建时间，默认最近 24 小时，
不是事件发生时间。`limit` 默认 100，范围 1–200；按创建时间/版本/事件 ID 倒序稳定排序，
额外读一条判断截断。资产时间排序有专用索引。

每条包含 revision、eventId、assetId、历史 groupId、reason（`candidate_limit` 或 `late`）、candidateCountLowerBound（`late` 为 0）、
windowFrom、windowTo、createdAt。只有保留期内且有权限的缺口可见，空列表不代表完整覆盖。
单条 SQL 使用数据库当前用户角色，同时校验历史组和当前资产组的 viewer 成员身份；
未分组资产只有全局管理员可读，管理员降权不使用请求上下文中的旧角色放行。
读取没有副作用，不会触发补检或清除缺口。

### 资产详情展示

「资产详情 → 检测缺口」按需加载最近 24 小时记录，可切换 1/6/24/72/168 小时，每 15 秒刷新。
有缺口时显示检测未完成警示，数量使用“≥ 下限”（迟到缺口显示“—”），展开可见规则版本、来源事件 ID、事件时间窗口和历史归组。
列表最多取 200 条并分页，截断明确提示缩短时间范围；失败单独显示重试，空列表不显示覆盖成功标记。

查询缓存包含当前用户/角色/成员信息和资产归组，关闭标签页后移除；中英文同步维护。
这只是缺口可视化，不提供补检或消除缺口按钮。前端类型检查、构建与 lint 通过，浏览器验收尚未进行。

## 无引用归档清理

现有 Janitor 在 `RETENTION_DAYS > 0` 时，按相同保留时长清理无引用的旧规则快照，每轮最多 1000 个，
复用 `RETENTION_INTERVAL_MINUTES` 周期；不会删除仍被候选、命中或检测缺口引用的版本。
入库读取已有归档时持有 `FOR KEY SHARE` 锁；清理使用 `FOR UPDATE SKIP LOCKED` 跳过正在使用的版本。
候选、命中和缺口对版本新增外键，数据库最终阻止删除被引用原文。

新增外键采用 `NOT VALID` 迁移：保护后续写入和引用删除，不伪造旧版缺失的原文，也不声称历史孤立引用已经修复。
已有历史缺失仍需单独审计；不存在真实原文时不能生成假的恢复记录。
当前活动版本若已无任何持久引用，也可以在超过保留期后清理；后续新事件会从内存完整快照再次持久化原文。
此清理不主动删除候选，不缩短迟到窗口，不删除仍有证据依赖的历史版本。
