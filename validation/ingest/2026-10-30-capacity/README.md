# 2026-10-30 入库容量阶梯验证

## 版本与范围

生产服务端 `be20c7f60`（双节点 HA，64 条批消息、32 分片、NATS 三副本、PostgreSQL 同步备库），
测试工具 `b9f95d1a0`，fixture `mixed-v2-process-identities`。
工具已部署到现有专用 Linux 测试机，使用其原有 mTLS 身份；服务端无需为此修改或重新部署。
服务端提交和工具提交的 CI 均通过，工具本地测试、静态检查、构建通过。

每轮 30 秒，在自然业务之外向同一测试资产额外发送事件。95% 进程、3% 网络、2% DNS；
全部带 process GUID 和 parent GUID，进程 GUID 写入数量逐轮核对；200/s 轮另核对父 GUID 为 6000/6000。
测试没有执行所描述的进程或网络连接，原始事件带明确测试标记。
方法、硬性上限与停止条件见 [入库容量验证](../../../docs/ingestion-capacity.md)。

## 瓶颈线索与下一步

- 第二轮 400/s 的 30 秒数据库等待采样中，事件 INSERT 的 `DataFileRead` 最多（97 个活动后端采样），
  其次可见 CPU、WAL 与同步复制等待。采样计数不是精确耗时比例。
- 应用容器 CPU 观察值约 6%/23%（Docker 单核百分比口径），没有 CPU quota，也未记录 CPU throttling。
- 沿实际应用数据库连接分别测 200 次 `SELECT 1`：两节点平均约 0.23/0.73 ms，
  P95 约 0.30/0.96 ms。这包含数据库执行与往返，不是纯网络 RTT。
- 本地真实规则集 Linux 基准约 8.4 μs/条、0 分配；测试硬件与生产不同，只作排查参考。
- 两节点 PostgreSQL `shared_buffers` 仍为 128 MB；宿主可见内存约 8 GB。
  事件索引体积超过可用缓存；普通 process GUID 索引约 2.4 GB，需核对其与 GUID/时间联合索引的查询覆盖。
  尚未调整数据库缓存、删除该索引或改变同步持久化策略。

下一步先减少被证明重复的写入/索引成本，并按相同样本复测。多资产、多分片、长时间稳定负载、
高告警率和故障期间容量仍未验收；本报告不给出整个 XDR 的容量上限或端到端 P95。
