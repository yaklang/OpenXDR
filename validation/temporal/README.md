# 时序检测回放

`cases.json` 是人工构造的归一化事件语料，使用仓库基础规则和 `temporal-rules/` 实验规则。
命令行仅作为事件文本参与匹配，测试不会执行命令、下载文件或修改主机。
`example.invalid` 与 `192.0.2.10` 是占位地址；不把本语料冒充真实攻击采集或 Atomic 测试实录。

从 `server/` 运行：

```sh
go test ./internal/temporal -run TestRepositoryTemporalCorpus -count=1 -v
# 使用独立测试 PostgreSQL，并配置 INTEGRATION_DATABASE_URL：
go test -tags integration -p 1 ./internal/ingest -run TestRepositoryTemporalRulesPersistLateReplay -count=1 -v
```

两个测试分别由现有 CI 的单测、集成测试步骤自动包含，不需要新增后台服务。

`auth-burst-cases.json` 是 `temporal-rules/wazuh-gap-*.yml` 六条认证规则的语料（阈值、窗口、乱序、重投、跨主机 / 跨组，
来源维度的分来源、缺来源、非法来源、IPv6 规范化），由同一个单元测试一并回放，另由
`go test -tags integration -p 1 ./internal/ingest -run TestAuthBurstPersistentReplay` 走数据库持久回放。

81 个确定性回放用例。最早的 30 个覆盖计数阈值/窗口边界、乱序、重投、成功认证负例，以及下载执行后敏感文件变更的
先后关系、同时间/反转/窗口外、跨组/跨主机、普通下载/普通文件负例和 OS 适用范围。
账号维度（`linux-account-auth-burst`，`min_assets: 2`）有 10 个专项：跨主机累计（含大小写/空白不同的同一账号）、乱序迟到、
十分钟窗口外、不跨组、不同账号不累计、无用户名不计入、成功登录不计入，以及单机多次不足两台资产、
迟到的另一台主机使不同资产数达标、单机持续失败后另一台主机一次（证据为窗口内全部计数事件）。
事件可选 `username` 字段，表示入库信封的 username 列（账号维度只认这一列）；省略表示无用户名。
原有认证用例补上了与原文一致的 username：同主机五次失败等单机用例只命中主机规则（账号规则要求至少两台资产），
「认证计数不跨主机」（两台主机共五次）在资产维度不命中、在账号维度命中，正好对照两种实体。
其余 42 个对应后来扩充的 18 条规则（爆破后侦察、侦察集中、下载执行后持久化、凭据读取后打包/外传/外联、
防御削弱后可疑执行及 Windows 对应链路），每条至少一个正例和一个贴近日常运维的良性对照：
良性对照都让链路中至少一步的基础规则真实命中（例行备份打包、包管理器装服务、监控脚本 `curl -d`、
安装后清历史/清 journal、按 k3s 文档关防火墙后 `curl | sh`、软件安装写 Run 键、资产盘点跑 ipconfig 等），
证明挡住的是关联而不是基础匹配本身；另有窗口外、跨账号与 Windows 排除项快照晚于下载（已知缺口）用例。
最后 10 个对应引用信号规则的两条：管道下载执行（`temporal` 不论先后）有同一时刻、shell 先被采到、`wget -qO- | sh -s` 带参数、
凑齐后再来探活不重复命中 4 个正例，以及探活 curl 与 6 秒后的子 shell、先下载到文件再执行 / `sh -c` / 登录 shell、跨主机 3 个对照；
「失败 → 成功 → 侦察」除复用原有「爆破得手后同账号执行侦察」正例外，有成功在失败之前、得手账号与侦察账号不同、
扫描爆破 root 而运维用自己账号登录排查 3 个对照。信号规则同样从原文匹配，不单独告警由集成测试核对。
每个事件先经过基础规则原文匹配，再转换为候选；语料不直接填入规则命中。
回放逐步按到达顺序求值，使用独立的事件时间，并在中途从规则归档重建快照。
核对规则 ID、终点 ID、完整有序证据，不只检查“是否有告警”。

数据库专项针对四条实际规则（账号规则的五次失败分布在同组三台主机上；管道下载执行两步都是信号规则，另核对没有信号告警），验证终点先到、处理器重建、前序补到及全部重投后，
持久命中只有一条、告警计数为 1，证据顺序正确。这覆盖处理器恢复，不模拟 OS 进程崩溃或电源故障。
原有数据库测试继续覆盖组切换、事务回滚、证据保留和并发；本语料不替代实机采集、容量测试或生产调优。
